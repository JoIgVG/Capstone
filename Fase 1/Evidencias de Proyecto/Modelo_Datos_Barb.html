Modelo de Datos Completo
Proyecto Barb — Plant Maintenance App
Especificación técnica de tablas, atributos y relaciones
Versión 1.0 — Mayo 2026

1. Introducción

Este documento presenta el modelo de datos rediseñado para el proyecto Barb (Plant Maintenance App), una aplicación para gestión de mantenimiento industrial que integra chat con documentación, diagnóstico asistido por IA, topología de planta y mantenimiento predictivo.

El modelo aquí especificado resuelve los 30 endpoints definidos en el documento "Plant Maintenance App — Backend API Documentation" y cubre los cuatro módulos funcionales del wireframe: Document Chat, Machine Debug, Plant Topology y Predictive Maintenance.

2. Resumen Ejecutivo

El modelo original propuesto resolvía aproximadamente el 40-50% de los endpoints. Las principales deficiencias detectadas fueron:

  • Falta de la entidad DISCIPLINA, eje central del chat con documentación.
  • Mezcla de la conversación y los mensajes en un único campo TEXT (deberían ser tablas separadas 1:N).
  • Ausencia total del módulo de topología de planta (nodos, conexiones, zonas, sensores).
  • REPORTE no existía como entidad propia.
  • Relación ORDEN_TRABAJO → REPUESTO definida como FK simple (debería ser muchos-a-muchos).
  • Sin soporte para preferencias de usuario, logs de actividad, adjuntos, ni mantenimiento predictivo.
  • Tabla DASHBOARD incorrectamente modelada como entidad (es una vista agregada).

El modelo propuesto agrega 22 tablas nuevas, refactoriza 7 tablas existentes y reorganiza el diseño en 9 módulos funcionales.

3. Índice de Tablas

Módulo 1 — Autenticación y Usuarios: USUARIO, AUTH_TOKEN, PREFERENCIA_USUARIO, LOG_ACTIVIDAD
Módulo 2 — Plantas y Máquinas: PLANTA, CATEGORIA_MAQUINA, MAQUINA, SENSOR
Módulo 3 — Documentación: DISCIPLINA, DOCUMENTO
Módulo 4 — Chat (Documentación y Debug): CONVERSACION, MENSAJE, FUENTE_MENSAJE, SESION_DEBUG, ADJUNTO
Módulo 5 — Diagnóstico y Reportes: DIAGNOSTICO, DIAGNOSTICO_CAUSA, DIAGNOSTICO_ACCION, REPORTE
Módulo 6 — Órdenes de Trabajo: ORDEN_TRABAJO, OT_REPUESTO, OT_AUDIT_LOG
Módulo 7 — Inventario: REPUESTO
Módulo 8 — Topología de Planta: TOPOLOGIA_NODO, TOPOLOGIA_CONEXION, TOPOLOGIA_ZONA, ZONA_NODO
Módulo 9 — Mantenimiento Predictivo: PROGRAMA_MANTENIMIENTO, EJECUCION_PROGRAMA, LECTURA_SENSOR

4. Convenciones

  • PK — Clave primaria.
  • FK — Clave foránea.
  • NUEVA — Tabla añadida respecto al modelo original.
  • MODIFICADA — Tabla del modelo original que requiere cambios.
  • Todos los timestamp usan formato ISO 8601 UTC.
  • Los IDs se modelan como BIGINT autoincremental (o UUID según preferencia del equipo).
  • Eliminaciones lógicas: la API actual no implementa soft deletes; las columnas estado permiten desactivar registros sin eliminarlos.

15. Notas de Implementación

  • Índices recomendados: todas las FK deben tener índice. Adicionalmente: USUARIO(email), USUARIO(username), AUTH_TOKEN(refresh_token), DOCUMENTO(disciplina_id, planta_id, maquina_id), MENSAJE(conversacion_id, timestamp), LECTURA_SENSOR(sensor_id, timestamp) — esta última se beneficia de particionamiento por fecha.
  • Eliminar la tabla DASHBOARD original: los KPIs del dashboard (GET /reports/dashboard-kpis) son agregados calculados sobre las tablas existentes, no entidades persistidas. Si se requiere caché, crear una tabla KPI_SNAPSHOT con (fecha, tipo, valor) o usar materialized views.
  • Diagnósticos vs Mensajes: un diagnóstico se asocia a un mensaje específico del asistente (el que lo generó), pero pueden generarse varios diagnósticos en una misma sesión. Por eso la FK DIAGNOSTICO.mensaje_id es opcional.
  • Soft delete: la API actual no lo implementa (los DELETE son físicos). Si se requiere, agregar columnas deleted_at NULLABLE y deleted_by a las tablas críticas.
  • Particionamiento: LECTURA_SENSOR, LOG_ACTIVIDAD y OT_AUDIT_LOG crecen indefinidamente — particionarlas por mes/año.
  • Integridad referencial: usar ON DELETE RESTRICT por defecto. Excepciones: ON DELETE CASCADE para MENSAJE→FUENTE_MENSAJE y CONVERSACION→MENSAJE.
